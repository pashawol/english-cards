# Plan — Haiku (контент): примеры использования в JSON-наборах

## Цель

В каждой карточке всех `data/*.json` (кроме `data/manifest.json`) добавить поле `examples` — массив из 2-3 примеров употребления конструкции, с переводом на русский.

## Зона ответственности

- Только: `data/*.json` (файлы наборов, без `data/manifest.json`)
- **Не трогать**: `app.js`, `styles.css`, `index.html`, `CLAUDE.md`
- **Не менять** в карточках поля: `ru`, `en`, `name` (на уровне файла), `category`, `categories`, `id` — только **добавлять** `examples`.

## Формат

К каждой карточке добавить поле `examples`:

```json
{
  "ru": "обвинять в",
  "en": "accuse of",
  "examples": [
    { "en": "They <b>accused</b> him <b>of</b> stealing the money.",
      "ru": "Они обвинили его в краже денег." },
    { "en": "She has been <b>accused</b> <b>of</b> lying.",
      "ru": "Её обвинили во лжи." }
  ]
}
```

## Правила к примерам

### 1. Количество
- **2-3 примера на карточку** (по умолчанию 2, для разнообразия — 3).
- **Для неправильных глаголов (файлы 21-24) — обязательно ровно 3**, по одному с каждой формой (V1 / V2 (Past Simple) / V3 (Past Participle)).

Пример для irregular verb:
```json
{ "ru": "видеть", "en": "see / saw / seen",
  "examples": [
    { "en": "I <b>see</b> you every day at the bus stop.",
      "ru": "Я вижу тебя каждый день на остановке." },
    { "en": "We <b>saw</b> a great movie yesterday.",
      "ru": "Мы посмотрели отличный фильм вчера." },
    { "en": "Have you ever <b>seen</b> the Northern Lights?",
      "ru": "Ты когда-нибудь видел северное сияние?" }
  ]
}
```

### 2. Выделение жирным
- Целевая конструкция целиком обёрнута в `<b>...</b>`.
- Если конструкция разрывается существительным/местоимением — каждая часть в **своих** `<b>` тегах.

Примеры:
- `accuse of` → `<b>accused</b> him <b>of</b>` или `<b>accused of</b>` (без разрыва)
- `blame smb for` → `<b>blame</b> her <b>for</b> the mistake`
- `bring up` (phrasal) → `<b>bring</b> him <b>up</b>` (минимум один пример с разрывом)

### 3. Phrasal verbs (файлы 13-16)
- **Минимум один пример** с разрывом конструкции дополнением (между частями phrasal verb).
- Второй пример может быть без разрыва, для естественности.

### 4. Verbs + prepositions (файлы 07-10, 11-12)
- **Хотя бы один пример** должен показывать схему `verb + (smb/smth) + preposition + object`, чтобы было видно как разрывается дополнением.

### 5. Adjectives + prepositions (файлы 04-06)
- Конструкция: `to be + adj + prep + object`. Примеры — `She is <b>afraid of</b> dogs.`

### 6. Articles (файлы 01-03)
- Здесь карточки уже содержат фразу с артиклем (например `a book`, `the sun`, `Ø London`). В примерах: использовать карточечную фразу в естественном предложении и подсветить **артикль + существительное** (или для zero-article — само существительное).

### 7. Time/Place/Movement prepositions (файлы 30-37)
- Конструкция: `prep + noun` (например `at night`, `in 2026`, `on Monday`). В примерах подсветить целиком, например `<b>at night</b>`.

### 8. RU перевод
- **Естественный**, не дословный. Должен звучать по-русски.
- Сохранять интонацию исходного предложения (вопрос → вопрос, прошедшее → прошедшее).
- Не выделять ничего жирным в RU.

### 9. Разнообразие
- В разных примерах одной карточки — **разные**:
  - времена (Present / Past / Present Perfect / Future / Conditional)
  - подлежащие (I / he / she / they / we / nouns)
  - дополнения (избегать одинаковых имён вроде «John» во всех примерах)
- Длина — не больше ~12 слов на пример.
- Без редкой/устаревшей лексики, чтобы пример был учебно понятен.

## Технические правила

- Не менять поля `ru`, `en`, `name`, `category`, `categories`, `id`, и порядок ключей внутри карточки кроме добавления `examples` после `en`.
- Сохранять отступ файла (2 пробела) и пустую строку в конце файла, если она есть.
- **Идемпотентность**: если у карточки уже есть непустое поле `examples` — пропускать её, ничего не менять.
- На выходе — валидный JSON. Проверка обязательна:
  ```bash
  node -e "JSON.parse(require('fs').readFileSync('data/XX-...json'))"
  ```
- Если файл получится больше 30-40 КБ, это нормально — проверка одна и та же.

## Порядок работы

1. По одному файлу за раз — чтобы не путать контекст.
2. После каждого файла — валидация JSON (см. выше). Если ошибка — исправить в этом же файле, потом идти дальше.
3. Коммитить **пачками по 5 файлов** на текущей ветке. Сообщение: `content: add examples to <file1>, <file2>, ..., <file5>` (или короче, если коротко).
4. После прогона всего батча — финальная валидация: пройтись циклом по всем файлам в `data/`.

## Если есть сомнения

- В точности конструкции (например, `agree with` vs `agree on` vs `agree to`) — оставлять то, что есть в `en` карточки, не «исправлять».
- В русском переводе — выбирать самый естественный вариант, не делать буквальный перевод.
- Если карточка многозначная (например `get` = «брать, получать, доставать») — показать **разные значения** в разных примерах.
